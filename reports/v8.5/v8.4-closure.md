## Fixed Or Closed

### Issue A: cmd pane mis-discovery

Status: resolved.

The managed cmd pane is explicitly tagged with `@ccb_role=cmd` and
`@ccb_slot=cmd`. The previous hypothesis that the operator was outside the CCB
session was retracted. The intended design is operator Claude as the cmd pane.

### Issue B: legacy `mailbox_state=active`

Status: fixed by PR-B.

Unknown mailbox states, including legacy `active`, decode as `idle` instead of
raising `ValueError`.

### Issue C: Codex readback/binding wedge

Status: fixed by PR-C.

Readback anchoring and binding diagnostics were hardened. Post-restart live
monitoring did not show fresh `bound_turn_contaminated=True` firing for the
tested round-trip path.

### Issue D: `pending_cmd_replies` metric ambiguity

Status: reclassified by PR-D.

`pending_cmd_replies` is a backlog/debug counter, not a cmd visible-delivery
acceptance gate. Fresh visible delivery, delivered-cache advancement, and ccbd
health are the v8.5 acceptance signals.

### Issue E: cmd visible delivery stall

Status: fixed by PR-E.

Durable delivered-cache rehydration prevents an old, evicted, already-surfaced
reply from permanently blocking fresh cmd visible delivery. The same PR also
adds a ccbd startup ownership guard so an old socket cannot satisfy readiness
for a newly spawned daemon.

## Deferred

### Issue F: agent3 Claude-provider context bleed

Status: deferred to v9, P1.

Agent3 can retain stale Claude session context and report relay outcomes that
do not match durable job state. This requires provider/session isolation and
attempt-state policy, which belongs in the v9 agent-message-management cycle.

Short-term rule: verify agent3 relay claims through `ccb pend <job_id>` or
durable mailbox state.

### Issue G: `cmd` as an `ccb ask` target

Status: open follow-up, P1.

The v8.4/v8.5 cmd work fixed reply delivery into the operator/cmd pane, but it
did not complete the separate goal of treating the operator pane as a first
class `ccb ask` target. Live verification showed:

```text
ccb ask cmd "..."
command_status: failed
error: unknown agent: cmd
```

The code already supports `cmd` as a mailbox owner and as an ask sender in some
paths, but the submission target path is still agent-only. This should not be
closed under Issue A. Issue A was about pane discovery/injection target
selection; Issue G is about accepting `cmd` as a submit target and routing the
request into the operator pane through the CCB control plane.

Short-term workaround: inject directly into the discovered cmd tmux pane only
for manual verification. Do not treat that as satisfying the CCB target
contract.
